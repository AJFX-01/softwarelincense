A1. The problem and the idea
----------------------------
- Every project needs a license, and every dependency brings its own license. Developers
  usually have no legal training, so they either pick a license that does not protect what
  they care about (e.g. permissive when they wanted improvements kept open) or one that
  conflicts with a dependency (e.g. closed-source app built on GPL code).
- Existing help does not fit: choosealicense.com gives a few generic paths, ignores
  dependencies and never explains "why for YOUR project"; scanners (ScanCode, etc.) audit
  after the fact instead of recommending; lawyers are slow and expensive.
- Idea: an LLM turns plain-language goals into license concepts and explains licenses in
  plain words. BUT LLMs state things confidently that the text does not support, and in
  licensing a confident wrong answer is worse than none. So every claim the LLM makes must
  cite and quote a license clause, and an independent NLI model checks the claim against that
  clause. The user sees each claim as verified / unverified / contradicted, with the clause
  one click away.
  WHY an independent checker: it does not share the LLM's mistakes, and its output doubles as
  an automatic faithfulness measure.

A2. From the proposal to "v1" (what we cut and why)
---------------------------------------------------
The proposal described a bigger neuro-symbolic system: rules engine, vector-store retrieval,
repository scanning, fine-tuned models, a hosted commercial LLM, expert validation.
Phase 1 built a smaller core ("v1": description and/or manifest -> LLM + NLI) that could be
built AND evaluated end to end:
- Open-weight LLM on Groq's free API instead of a paid hosted model. WHY: cost, and
  open weights are reproducible.
- Keyword/anchor clause selection instead of vector retrieval. WHY: we only need the clauses
  that express a license's labelled obligations, the labels tell us which ones, and full
  license texts (GPL-3.0 is ~35,000 chars) exceed Groq's 8,000 tokens/minute free limit.
- Package-registry metadata (PyPI, npm) instead of scanning repositories. WHY: simpler and
  the declared license is what a developer sees.
- No fine-tuning in Phase 1. WHY: get a measured baseline first.
- Expert-free ground truth from curated public data. WHY: the instructor stressed we have no
  legal expert, so evaluation must not depend on one.
- Rules engine + OSADL compatibility matrix deferred to Phase 2 (Phase 1 results showed they
  are needed, see A11).

A3. Research questions
----------------------
RQ1 Requirement-to-license mapping: how well can an open-weight LLM, given a license
    catalogue, map natural-language requirements to licenses that satisfy them, and how does
    accuracy change with how specific the request is (size of the correct-license set)?
RQ2 Claim verification: how reliably can off-the-shelf NLI models verify LLM claims against
    the clauses they cite, measured on human-validated clause-claim pairs?
RQ3 Explanation faithfulness: how grounded are the explanations in the cited text (quotes
    found verbatim, entailment), and how does verification change what users see compared
    with an unverified baseline? (Phase 1: preliminary only.)
WHY these three: each can be answered from computed or checkable ground truth (A1, A6, A7),
which is the expert-free constraint.

A4. Data sources and why each one
---------------------------------
1. choosealicense.com repository (47 license files: YAML header + full text).
   Kept: SPDX id, title, description, the 3 label lists, full text. Dropped website-only
   fields. Label vocabulary: 5 permissions (commercial-use, modifications, distribution,
   private-use, patent-use), 8 conditions (include-copyright, include-copyright--source,
   document-changes, disclose-source, same-license, same-license--file,
   same-license--library, network-use-disclose), 4 limitations (liability, warranty,
   trademark-use, patent-use).
   WHY: curated, consistent, machine-readable labels = the facts all ground truth is
   computed from. This is what makes the evaluation expert-free.
2. SPDX license list v3.29.0 (740 ids, OSI-approved flag) -> data/processed/spdx_ids.json.
   WHY: to scope the catalogue (OSI flag) and to normalise dependency licenses to SPDX ids.
3. Software Heritage license dataset (Zenodo 6379164): 6.5M deduplicated license files.
   Used the 5 metadata tables + the published 20,000-file random text sample, joined on SHA1
   and SWHID -> 20,000 rows x 16 columns (data/processed/sample20k_index.csv). Did NOT
   download the 14 GB full-text archive.
   WHY: real-world usage evidence for exploratory analysis and to check our scope covers
   what people actually use. It is NOT ground truth: it says which license a file is, not
   what a license requires, and has no labels. ("Why not use it instead of choosealicense?"
   - because it has texts but no permission/condition/limitation labels.)
4. PyPI / npm registries at run time (license_expression, license, trove classifiers;
   npm "license"), normalised with exact SPDX matching + 41 common spellings (deps.py).
   Dev-only dependencies ignored. WHY ignored: they are not shipped, so their licenses do not
   bind the product. Unrecognised licenses are reported as UNKNOWN, never guessed.

A5. Knowledge base, scope and clauses
-------------------------------------
- Scope 47 -> 34: removed 8 not meant for software (media, docs, data, fonts, hardware) and
  5 not OSI-approved. WHY: the tool recommends software licenses; OSI approval is the usual
  meaning of "open source" and avoids recommending licenses with disputed status.
- Coverage check: 93.8% of Software Heritage sample files that have any detected license use
  one of our 34. WHY it matters: shows the small scope still covers almost all real usage.
- Copyleft classes from labels: permissive 21, weak copyleft 4, strong copyleft 9.
- Language check: CeCILL-2.1 is French-only. It stays recommendable but its claims cannot be
  verified (English NLI model), and the UI says so.
- Clause segmentation (licensewise/clauses.py): split at blank lines, drop non-English
  paragraphs, merge short headings into the next paragraph, attach a paragraph ending in ":"
  (lead-in) to each list item below it. Result: 812 clauses from 33 English licenses, median
  329 chars, all under the verifier's 512-token limit.
  WHY clauses: (1) the NLI model takes max 512 tokens; (2) a claim must be checked against the
  one passage that supports it; (3) users need a specific passage as evidence. WHY the lead-in
  fix: without it a clause stopped at "...you must do the following:" and lost its meaning.
- Clause for a label: per label an exact "anchor" pattern (e.g. "Limitation of Liability")
  and a broader keyword pattern; rank clauses by anchor hits, keyword hits, then position.
  Hand-checked on MIT, BSD, Apache-2.0, GPL-3.0, MPL-2.0. Same function picks Stage 2
  evidence at run time.
- Known defect: in AFL-3.0 and OSL-3.0, numbered sections "2)", "3)" after section 1 are read
  as list items of section 1's lead-in, so those clauses start with an irrelevant sentence.
  Left as a limitation in Phase 1.

A6. The v1 pipeline (licensewise/) and why each choice
------------------------------------------------------
Steps: input -> dependency lookup -> Stage 1 recommend -> clause retrieval -> Stage 2
explain -> NLI verify -> response.
- LLM: openai/gpt-oss-120b on Groq, zero-shot (instructions + catalogue, no examples, no
  training). WHY: strongest open-weight model on the free tier with strict JSON-schema output.
- Strict JSON schema via Pydantic for every LLM call; Stage 1 license ids are a Literal of the
  34 ids and exactly 3 recommendations are required; a duplicate triggers one retry.
  WHY: the model cannot invent a license or return a malformed answer; 3 gives the user a
  choice and gives us Hit@1/Hit@3. (Bug found: it once returned 0 recs / duplicates -> fixed
  with min_length=max_length=3 + retry.)
- Stage 1 also returns the requirements it understood, dependency conflicts and clarifying
  questions. WHY: transparency (user sees what the model understood) and FR7/FR8.
- Stage 2 gets only the clauses for the license's labelled obligations (<= 12,000 chars), and
  must write 3-5 one-sentence claims each citing ONE clause id + an exact quote <= 300 chars.
  WHY: full texts break the 8k tokens/minute limit; quoting forces grounding.
- Verifier: (1) quote check - the quote must appear in the cited clause (ignoring case,
  whitespace, quote style) else "unverified"; (2) DeBERTa NLI with premise = whole clause,
  hypothesis = claim; entailment -> verified, neutral -> unverified, contradiction ->
  contradicted. WHY whole clause: that is how the verifier was evaluated in RQ2.
- If more than half of a license's claims fail, Stage 2 is re-run once with the failed claims
  listed; the retry is kept only if it verifies more. WHY: cheap self-correction, bounded cost.
- Disclaimer "based on license text only, not legal advice" on every result (safety NFR).
- Other models (evaluation only): Qwen3.8-27B writes test descriptions, gpt-oss-20b checks
  them. WHY different models: the system should not be tested on its own phrasing.
- NLI models (both pre-trained by others, NOT trained by us in Phase 1):
  MoritzLaurer/DeBERTa-v3-large-mnli-fever-anli-ling-wanli (chosen) and
  FacebookAI/roberta-large-mnli (baseline). Run locally on Apple MPS.
- Free-tier limits that shaped everything: ~8k tokens/min, 1k requests/day, 200k tokens/day
  for gpt-oss-120b; Qwen 1k output tokens/min (so max_tokens 1000 for it).

A7. Ground truth for RQ1: profiles and descriptions
---------------------------------------------------
- No public dataset pairs developer requests with correct licenses, so we computed one.
- Six requirements chosen from the labels that (a) differ between our licenses and (b) a
  developer would actually state: share changes (don't care / none / file-or-library /
  whole work), network use (don't care / must trigger sharing / must not), patent grant,
  trademark protection, no attribution required, no obligation to document changes (each
  don't care / required).
  WHY not all 17 labels: labels every license has (commercial use, warranty disclaimer) or
  none has cannot tell licenses apart.
- Combinations: 4 x 3 x 2 x 2 x 2 x 2 = 192 (not 2^6 = 64, because share_changes has 4
  settings and network_use 3). Minus the empty request = 191. For each, the answer key = all
  in-scope licenses whose labels satisfy every requirement. 114 have no license -> dropped ->
  77 profiles, 1-29 correct licenses each (median 3).
- Descriptions: Qwen3.8-27B wrote ~3 first-person descriptions per profile, each with a
  different persona and project type and never naming a license. gpt-oss-20b then read each
  description WITHOUT the profile and listed the requirements; kept only exact matches
  (round-trip check). 235 written (writer sometimes gave more/fewer than 3: P056 had 9, P033
  4, P015 2, P040 1), 190 passed (81%), covering 70 of 77 profiles. 122 distinct personas.
  WHY descriptions and not the profile JSON: (1) real users write prose, not requirement
  lists; (2) with structured requirements a simple label lookup - the same one that builds
  the answer key - would solve the task and the LLM would be pointless; (3) giving the model
  the profile would leak the answer. WHY personas: tests understanding of meaning rather than
  one phrasing. WHY round-trip check: removes descriptions that do not actually express the
  profile, so a "miss" is the recommender's fault, not the test's.

A8. Ground truth for RQ2: clause-claim pairs and human labels
-------------------------------------------------------------
- 16 claim templates (17 labels minus private-use, which no license states in one clause),
  each with a true and a negated sentence. For every English license and every label it
  has: the label's clause + true claim (entailment), + negated claim (contradiction), + a
  true claim about another label whose keywords are not in the clause (neutral).
- 266 license-label combinations, 23 had no matching clause (mostly commercial use: e.g. BSD
  never mentions selling) -> 243 -> 729 pairs (243 per class), on 173 distinct clauses
  (of the 812). Claims and labels come from templates, not from a model.
  WHY templates: labels are known by construction, so the set is large and cheap; the human
  check then measures how often that construction is wrong.
- Human validation: stratified random 150 pairs (50 per class). Two annotators, 75 each,
  judging only from the clause: the first author, and a software engineer with experience
  working with open-source licenses who is now a software-engineering researcher.
  22 disagreements with the auto labels were settled by the team, 3 stayed ambiguous and were
  excluded -> 146 human-labelled pairs. The clause fix later changed 23 sampled pairs, which
  were relabelled (127 carried over: 96 unchanged, 31 lead-in only).
- Agreement: each annotator also labelled 20 of the other's pairs; 39 usable double-labelled
  pairs, 92.3% agreement, Cohen's kappa 0.88 ("almost perfect"). Caveat: the second label was
  given with the first visible, which may inflate kappa.
- Auto labels agree with the final human labels on 143/146 = 97.9%, so the full 729 can be
  trusted for model comparison.

A9. Evaluation protocol and metrics
-----------------------------------
- RQ1: Stage 1 gets only the description + catalogue. Hit@1 (first pick correct), Hit@3 (any
  of 3 correct), Precision@3 (share of 3 correct), violation rate per requirement, grouped by
  answer-key size 1-3 / 4-10 / >10 (= request specificity). Because of the 200k tokens/day
  limit we ran one description per profile first, shuffled, resumable, waiting on quota, and
  stopped at 104 descriptions covering all 70 profiles. WHY one-per-profile-first: every
  profile is represented even if the quota stops us early.
- RQ2: both NLI models on all 729 pairs (premise = clause, hypothesis = claim). Accuracy,
  per-class P/R/F1, macro-F1, against auto labels and against the 146 human labels.
  Key metric: entailment precision = how often "verified" is right.
- RQ3: quotes found verbatim + verified/unverified/contradicted split on full runs.

A10. Results
------------
Exploratory (Software Heritage 20k sample): 52% of files have exactly one in-scope license,
6% a likely modified license, 8% several, 4% only out-of-scope, 28% none (mostly AUTHORS
files and HTML). MIT 70.5% of in-scope files, then BSD-3-Clause 6.9%, Apache-2.0 6.2%,
GPL-2.0 4.6%, GPL-3.0 4.1%; 488 distinct license ids; ScanCode confidence mean 99.1.
RQ1 (104 descriptions): Hit@1 0.56, Hit@3 0.74, Precision@3 0.55.
  answer key 1-3 (n=47): Hit@1 0.40, Hit@3 0.60 | 4-10 (n=35): 0.54 / 0.77 |
  >10 (n=22): 0.91 / 1.00.
  Violations: trademark 54%, document changes 39%, share changes (copyleft level) 21%,
  network use 12%, patent 4%, attribution 0%. Apache-2.0 was first pick for 30 of 104.
RQ2 (146 human pairs): DeBERTa accuracy 0.815, macro-F1 0.816, entailment precision 0.944,
  recall 0.694; RoBERTa 0.733 / 0.729 / 0.900 / 0.551. On 729 auto pairs: 0.809 vs 0.782.
  DeBERTa confusion (rows human): entailment 34/14/1, neutral 2/41/4, contradiction 0/6/44.
  Never marked a contradiction as entailed. Main weakness: 29% of true claims left
  "unverified". Recall by label is high for document changes (91%), liability (90%),
  distribution (84%), low for commercial use (21%), same-license (25%), network use (25%) -
  licenses say "sell"/"charge a fee", not "commercial use".
RQ3 (2 full runs, 19 claims): 100% quotes verbatim; 11 verified, 7 unverified, 1
  contradicted (an accurate paraphrase of AGPL-3.0 s.6, i.e. a verifier false positive).
Interpretation:
- The LLM handles broad requests but fails on specific ones, and its errors are on FACTS
  already in the labels (trademark, document changes) -> a deterministic check / rules engine
  should do the matching (Phase 2 direction).
- The verifier is cautious; in licensing a wrong "verified" costs more than a missing one, so
  this error profile is acceptable if the UI presents "unverified" as "not confirmed".

2026-11-06  ML-5: entailment threshold tuning (scripts/tune_nli_threshold.py)
-----------------------------------------------------------------------------------------
- Rule: verified if P(entailment) >= t, else the larger of neutral/contradiction.
  t swept 0.05-0.95. Chosen on the 583 pairs WITHOUT human labels (auto labels) as the best
  macro-F1 that keeps entailment precision >= 0.90; reported on the 146 human pairs, which
  play no part in the choice. WHY the 0.90 floor: faithfulness NFR - a wrong "verified" is
  the costly error.
- DeBERTa: chosen t = 0.10.
    human test  argmax (Phase 1): acc 0.815, macro-F1 0.816, P(ent) 0.944, R(ent) 0.694
    human test  t = 0.10        : acc 0.829, macro-F1 0.830, P(ent) 0.925, R(ent) 0.755
  -> 9% more true claims confirmed for a 2-point precision cost, still above 0.90.
- RoBERTa (baseline): chosen t = 0.30: acc 0.733 -> 0.747, P(ent) 0.900 -> 0.879,
  R(ent) 0.551 -> 0.592 (falls below the 0.90 floor on the test set).
- Output: data/processed/nli/threshold_predictions_*.json (curve + test metrics).
- Not yet applied in licensewise/verifier.py; decide after ML-6 (fine-tuned model may need
  its own threshold).

2026-11-06  ML-6: fine-tuning DeBERTa on our pairs (scripts/finetune_nli.py) - IN PROGRESS
-----------------------------------------------------------------------------------------
- Machine has 8 GB unified memory; full fine-tuning of DeBERTa-v3-large needs ~7 GB for
  AdamW states alone, so only the top K encoder layers + pooler + classifier are trained.
  K is a hyperparameter (K=0 = head only). WHY not a smaller model: the large model's NLI
  pre-training is what makes it good; partial fine-tuning keeps it.
- Evaluation: 5-fold cross-validation GROUPED BY LICENSE, so every prediction comes from a
  model that never saw that license. Out-of-fold predictions for all 729 pairs.
  Hyperparameters compared on the 583 non-human pairs; the 146 human pairs are the test set.
  Training targets: human label where available, else auto label.
  WHY grouped: random splits would put the same clause (with a different claim) in train and
  test, inflating scores.
- Second check, --group label: folds by license LABEL, so the claim templates of a held-out
  label are never seen. WHY: our claims come from 16 templates; a model could memorise the
  templates instead of learning to read clauses. This stress test is closer to new claim
  wording from Stage 2.
- Grid planned: K in {2, 4, 8} at lr 2e-5, 3 epochs, batch 8; then best K with lr 1e-5 and
  5e-5; then the label-grouped stress test; then threshold tuning (ML-5) on the best
  out-of-fold predictions. Results: data/processed/nli/finetune/results.json.
- Before any training ran, the API/UI dev servers were stopped to free memory.
- Problem: the first attempt (whole model loaded, lower layers frozen) stalled - the machine
  was swapping ~13 GB, no epoch finished in 6 minutes. Freezing alone does not help because
  the full 1.7 GB model still runs forward every step.
- Fix: the frozen bottom 24-K layers give the same output for a pair every time, so they are
  run ONCE over all 729 pairs and their output cached on disk (data/processed/nli/finetune/
  cache/layer<24-K>.pt, ~185 MB, gitignored); training loads only the top K layers.
  Mathematically the same as training the whole model with those layers frozen.
- Sanity check before training: the untrained cached-bottom + top-4 model reproduced the
  Phase 1 DeBERTa predictions on 729/729 pairs (max probability difference 0.0016, the
  float16-vs-float32 rounding). Took 49 s instead of stalling.
- Precision: the checkpoint is float16 (transformers 5 keeps it, so Phase 1 ran in float16).
  Cached frozen outputs stay float16 like the baseline; trainable layers are loaded in
  float32 because AdamW updates in float16 are unstable.
- Second slowdown: even with caching, epoch 1 took 13 min, then 33 min after a padding fix.
  A 15-step benchmark showed the step itself is fast (0.61 s on MPS, 0.99 s on CPU) but MPS
  memory reached 3.3 GB after 15 steps: PyTorch's MPS allocator keeps buffers for every batch
  shape, so memory grows until the machine swaps. Fix: torch.mps.empty_cache() every 20
  steps. Epoch time 33 min -> 63 s, identical loss (0.3918), so results are unaffected.
  Also: batches are now groups of similar-length pairs (shuffled order) to cut padding, and
  the model loads in float16 with only the trainable top cast to float32.
  Lesson: on an 8 GB Mac, benchmark a few steps before launching a long run.
- The Mac went to sleep overnight (pmset log: repeated "Maintenance Sleep" from 04:03), which
  is why K=4 took 185 min wall-clock instead of ~17. Runs now start under `caffeinate -i`.
